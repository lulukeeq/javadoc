课程里如果默认数据完整，通常会优先使用 `INNER JOIN`

## 四、原始方式分页查询

### 1. 前端传递参数

分页查询时，前端需要传递：

- `page`
- `pageSize`

含义：

- `page`：页码
- `pageSize`：每页记录数

### 2. 后端返回结果

分页查询时，后端核心返回：

- `rows`：当前页数据列表，类型通常是 `List`
- `total`：总记录数，类型通常是 `Long`

一句话理解：

> 原始分页查询的核心输入是 `page` 和 `pageSize`，核心输出是 `rows` 和 `total`。

### 3. 为什么要封装 `PageResult<T>`

因为分页查询需要统一返回：

- `total`
- `rows`

所以需要封装一个通用分页结果类：

```java
PageResult<T>
```

核心字段通常是：

```java
private Long total;
private List<T> rows;
```

### 4. 分页查询 SQL 思路

原始分页查询通常拆成两部分：

1. 用 `COUNT(*)` 查询总记录数
2. 用 `LIMIT` 查询当前页数据

一句话理解：

> 原始分页查询通常不是一条 SQL 搞定，而是先查总数，再查当前页数据。

### 5. 起始索引计算

分页起始索引公式：

```text
start = (page - 1) * pageSize
```

注意：

- 必须带括号
- 不能写成 `page - 1 * pageSize`

### 6. Mapper 层职责

在 `EmpMapper` 中定义两个核心方法：

```java
public long count();
public List<Emp> list(Integer start, Integer pageSize);
```

说明：

- `count()`：查询总记录数
- `list(start, pageSize)`：查询当前页数据

这里 Mapper 不直接关心第几页，只关心：

- 从哪一条开始查
- 查多少条

### 7. SQL 还需要稳定排序

分页查询除了 `LIMIT`，通常还要加：

```sql
ORDER BY e.update_time DESC
```

作用：

- 保证分页结果顺序稳定
- 让最新修改的数据优先显示

### 8. Controller 层职责

Controller 方法可以写成类似：

```java
public Result page(Integer page, Integer pageSize)
```

前提：

- 前端参数名和后端方法形参名保持一致

如果想更稳一点，可以加默认值：

```java
@RequestParam(defaultValue = "1")
@RequestParam(defaultValue = "10")
```

作用：

- 前端未传参数时也能正常分页查询

### 9. Service 层职责

在 `EmpServiceImpl` 中完成分页核心逻辑：

1. 注入 `EmpMapper`
2. 调用 `empMapper.count()` 查询总记录数
3. 计算 `start = (page - 1) * pageSize`
4. 调用 `empMapper.list(start, pageSize)` 查询当前页数据
5. 封装 `PageResult`
6. 返回结果

### 10. Controller 调用链

Controller 中通过：

```java
empService.page(page, pageSize)
```

获取：

```java
PageResult<Emp>
```

然后再把它封装进统一响应对象 `Result` 中返回给前端。

一句话理解：

> Controller 负责接参数和响应结果，Service 负责分页业务逻辑，Mapper 负责查数据库。

### 11. 测试

原始分页代码写完后，需要：

- 重启服务
- 使用 Apifox 测试接口

重点验证：

- 参数是否正确接收
- `total` 是否正确
- `rows` 是否正确
- 部门名称是否联表查出来

## 五、PageHelper 分页插件实现

这一阶段的目标是：

> 在理解原始分页原理的基础上，用 PageHelper 简化分页代码实现。

### 1. PageHelper 使用步骤

PageHelper 的基本使用步骤：

1. 在 `pom.xml` 中引入 PageHelper 依赖
2. Mapper 接口定义普通查询方法，不考虑分页参数
3. 在 Service 中调用 `PageHelper.startPage(page, pageSize)` 开启分页
4. 调用 Mapper 查询数据
5. 解析结果并封装成 `PageResult`

### 2. 改造后的 select 变化

使用原始方式分页时，SQL 中通常需要手动写：

- `LIMIT`
- 分页参数

例如：

```sql
SELECT e.*, d.name AS deptName
FROM emp e
INNER JOIN dept d
ON e.dept_id = d.id
ORDER BY e.update_time DESC
LIMIT #{start}, #{pageSize}
```

使用 PageHelper 后，分页交给插件处理，Mapper 中的 `select` 会回归成普通查询 SQL：

```sql
SELECT e.*, d.name AS deptName
FROM emp e
INNER JOIN dept d
ON e.dept_id = d.id
ORDER BY e.update_time DESC
```

说明：

- 联表逻辑保留
- 排序逻辑保留
- 查询字段保留
- 不再手动写 `LIMIT`

一句话理解：

> 使用 PageHelper 后，Mapper 中的 `select` 不再手动处理分页，SQL 只保留正常查询、联表和排序逻辑，分页由插件自动完成。

### 3. Service 中使用 PageHelper 的三步操作

在 `EmpServiceImpl` 中，使用 PageHelper 的核心流程可以概括成三步：

1. 设置分页参数
2. 执行查询
3. 解析查询结果并封装返回

对应代码思路：

```java
PageHelper.startPage(page, pageSize);
List<Emp> empList = empMapper.list();
Page<Emp> p = (Page<Emp>) empList;
return new PageResult<Emp>(p.getTotal(), p.getResult());
```

### 4. 为什么可以强转成 `Page<Emp>`

虽然 Mapper 方法表面上返回的是：

```java
List<Emp>
```

但由于前面已经执行了：

```java
PageHelper.startPage(page, pageSize);
```

所以这次查询结果实际上已经带有分页信息，因此可以强制转换成：

```java
Page<Emp>
```

再通过：

- `p.getTotal()` 获取总记录数
- `p.getResult()` 获取当前页数据列表

### 5. 与原始方式相比的变化

使用原始方式时，需要自己：

- 调用 `count()`
- 计算 `start`
- 传递 `start` 和 `pageSize`

使用 PageHelper 后：

- 不再手动调用 `count()`
- 不再手动计算 `start`
- 不再向 Mapper 传递 `start`
- 由插件自动完成分页处理

### 6. Controller 层是否需要修改

这一阶段中，Controller 层通常不需要改动。

原因：

- 分页参数仍然是 `page` 和 `pageSize`
- 返回结果仍然是 `Result` 包装 `PageResult`
- 变化主要发生在 Service 和 Mapper 层

### 7. 测试

PageHelper 代码修改完成后，需要：

- 重启服务
- 使用 Apifox 测试接口

重点验证：

- 接口仍然能正常接收 `page` 和 `pageSize`
- 分页结果中的 `total` 是否正确
- 当前页数据 `rows` 是否正确
- SQL 联表查询出的部门名称是否仍然正常

一句话理解：

> 使用 PageHelper 后，分页实现被简化了，但接口的输入输出形式对前端来说基本不变。

### 8. 为什么 `List<Emp>` 可以强转成 `Page<Emp>`

虽然代码里写的是：

```java
List<Emp> empList = empMapper.list();
```

但由于执行查询前已经调用了：

```java
PageHelper.startPage(page, pageSize);
```

所以这次查询返回的结果，底层实际上是带分页信息的 `Page<Emp>` 对象。

可以理解成：

- `Page<E>` 是一种特殊的 `List<E>` 实现
- 所以查询结果虽然可以用 `List<E>` 接收
- 但它本质上仍然可以强转成 `Page<E>`

后面就可以通过：

- `p.getTotal()` 获取总记录数
- `p.getResult()` 获取当前页数据

### 9. PageHelper 的实现机制

PageHelper 的实现机制可以先理解成四步：

#### 第一步：记录分页参数

调用：

```java
PageHelper.startPage(page, pageSize);
```

这一步不会立刻查询数据库，而是先把“页码”和“每页条数”记录下来。

#### 第二步：拦截下一条 MyBatis 查询

当代码执行到：

```java
empMapper.list();
```

MyBatis 准备执行 SQL 时，PageHelper 作为 MyBatis 插件会拦截这次查询。

#### 第三步：自动改写分页 SQL

PageHelper 拦截查询后，会自动完成原始分页方式里的两部分工作：

1. 生成总数查询，用来获取 `total`
2. 给原查询追加分页限制，用来获取当前页数据

也就是说，原本需要自己手动写的：

- `COUNT(*)`
- `LIMIT`

现在由插件自动处理。

#### 第四步：把结果封装成 `Page<E>`

查询完成后，返回结果虽然可以用 `List<E>` 接收，但实际底层已经是带分页信息的 `Page<E>` 对象，因此可以强转后获取：

- `total`
- `result`

一句话理解：

> `startPage()` 先记录分页参数，等 MyBatis 执行下一条查询时，PageHelper 插件拦截 SQL，自动生成 count 查询并追加 limit，最后把结果封装成 `Page<E>` 返回。

### 10. 使用 PageHelper 的顺序要求

`PageHelper.startPage(page, pageSize)` 必须写在查询语句前面。

例如：

```java
PageHelper.startPage(page, pageSize);
List<Emp> empList = empMapper.list();
```

这个顺序不能反。

可以先理解成：

> PageHelper 通常只会对它后面的第一条查询生效。

进一步理解：

> PageHelper 仅仅会对紧跟在它后面的第一条查询语句进行分页处理。

这意味着：

- `startPage()` 调用后，要立刻执行目标查询
- 不要在中间插入其他无关查询
- 如果中间先执行了别的查询，分页效果就可能作用到错误的 SQL 上

因此，推荐写法要保持紧凑：

```java
PageHelper.startPage(page, pageSize);
List<Emp> empList = empMapper.list();
```

### 11. 使用 PageHelper 时，`@Select` 语句末尾不要加分号

使用 PageHelper 时，`@Select` 注解中的 SQL 末尾不要加分号 `;`。

例如：

```java
@Select("select * from emp")
```

不要写成：

```java
@Select("select * from emp;")
```

原因：

- PageHelper 会拦截并改写 SQL
- 它可能需要继续生成 count 查询或追加分页限制
- 分号通常表示 SQL 语句结束
- 如果 SQL 已经被手动写成结束态，插件后续处理时就容易出问题

一句话理解：

> 在数据库客户端里，分号通常表示语句结束；而在框架 SQL 中，PageHelper 还需要继续改写 SQL，所以不要提前加分号。

## 六、条件分页查询

### 1. 条件分页查询的本质

条件分页查询不是重写一套新的分页逻辑，而是在原有分页查询基础上加入查询条件。

一句话理解：

> 条件分页查询本质上是“带条件的分页查询”，也就是先按条件过滤，再对过滤结果做分页。

### 2. 查询条件来源

前端通过 `params` 传递查询条件。

当前常见条件包括：

- `name`
- `gender`
- `begin`
- `end`

所以后端需要同时接收：

- 分页参数
- 查询条件参数

### 3. Controller 参数接收方式

Controller 中仍然使用原来的分页方法：

```java
public Result page(...)
```

但会在原有分页参数的基础上新增查询条件参数。

典型写法：

```java
public Result page(
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "10") Integer pageSize,
        String name,
        Integer gender,
        @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate begin,
        @DateTimeFormat(pattern = "yyyy-MM-dd") LocalDate end) {
}
```

说明：

- `page`、`pageSize`：分页参数
- `name`、`gender`、`begin`、`end`：查询条件参数

### 4. 日期参数格式说明

当前端传递的是日期字符串时，如果后端要使用 `LocalDate` 接收，就需要：

```java
@DateTimeFormat(pattern = "yyyy-MM-dd")
```

作用：

- 指定前端日期字符串的解析格式
- 让 Spring 能正确把字符串转换成 `LocalDate`

一句话理解：

> 条件分页查询中，如果 `begin` 和 `end` 使用 `LocalDate` 接收，就需要通过 `@DateTimeFormat` 指定日期格式。

### 5. 模糊查询参数的写法

条件分页查询中，如果需要按姓名做模糊查询，不能直接写成：

```xml
e.name like '%#{name}%'
```

正确写法是：

```xml
e.name like concat('%', #{name}, '%')
```

原因：

- `#{name}` 是预编译参数，占位符和 `%` 直接混写会直接报错
- `concat('%', #{name}, '%')` 明确表示在 SQL 层进行字符串拼接

一句话理解：

> MyBatis 中模糊查询不能写成 `like '%#{name}%'`，正确写法是 `like concat('%', #{name}, '%')`。

### 6. 请求参数接收优化方案

当 Controller 方法参数越来越多时，可以把多个请求参数封装成一个对象统一接收。

例如可以定义：

```java
@Data
public class EmpQueryParam {
    private Integer page = 1;
    private Integer pageSize = 10;
    private String name;
    private Integer gender;

    @DateTimeFormat(pattern = "yyyy-MM-dd")
    private LocalDate begin;

    @DateTimeFormat(pattern = "yyyy-MM-dd")
    private LocalDate end;
}
```

然后 Controller 可以改成：

```java
public Result page(EmpQueryParam empQueryParam) {
    log.info("分页查询，参数：{}", empQueryParam);
    PageResult<Emp> pageResult = empService.page(empQueryParam);
    return Result.success(pageResult);
}
```

这样做的好处：

- 方法签名更短
- 分页参数和查询条件更集中
- 后续如果继续增加条件，只需要在参数对象中新增字段
- Controller、Service 的参数传递更统一

一句话理解：

> 当条件分页查询参数较多时，可以使用 `EmpQueryParam` 这样的参数对象统一接收请求参数，让代码更简洁、更易维护。

### 7. `EmpMapper` 的改造方向

进入条件分页查询后，`EmpMapper` 不再只是无参普通查询，而是需要能够接收查询条件参数。

如果使用参数对象封装方案，那么 `Mapper`、`Service` 都可以围绕 `EmpQueryParam` 继续传递参数。

这一阶段的重点不是重新设计分页方式，而是：

- 保留原有分页能力
- 在查询 SQL 中加入条件参数
- 使用动态 SQL 根据参数是否为空决定条件是否参与查询

一句话理解：

> 条件分页查询中，分页逻辑没有变，变化的是 `EmpMapper` 的查询条件传递方式和 SQL 结构。

### 8. 动态 SQL 的两层含义

条件分页查询中的动态 SQL，可以分成两层理解：

#### 第一层动态

参数值动态替换：

```xml
#{name}
#{gender}
#{begin}
#{end}
```

这表示 SQL 中的条件值不再写死，而是由前端传入参数动态提供。

#### 第二层动态

条件本身是否出现也要动态决定。

例如：

- 有 `name` 才拼姓名模糊查询
- 有 `gender` 才拼性别条件
- 有 `begin` 和 `end` 才拼时间范围条件

一句话理解：

> 动态 SQL 不只是参数值动态替换，更重要的是 SQL 条件本身是否出现，也要根据参数是否为空动态决定。

### 9. `<if>` 的作用

`<if>` 用来判断单个条件是否成立。

如果 `test` 条件为 `true`，就拼接这段 SQL；如果不成立，就不拼接。

例如：

```xml
<if test="gender != null">
    and e.gender = #{gender}
</if>
```

表示：

- 只有 `gender` 有值时，才按性别筛选

在员工条件分页查询中，常见用法包括：

```xml
<if test="name != null and name != ''">
    e.name like concat('%', #{name}, '%')
</if>

<if test="gender != null">
    and e.gender = #{gender}
</if>

<if test="begin != null and end != null">
    and e.entry_date between #{begin} and #{end}
</if>
```

一句话理解：

> `<if>` 负责控制单个条件要不要参与查询。

### 10. `<where>` 的作用

`<where>` 用来根据查询条件决定是否生成 `where` 关键字，并自动去掉条件前面多余的 `and` / `or`。

如果只使用多个 `<if>` 而手动写死 `where`，就可能出现：

```sql
where
and e.gender = 1
```

这种错误写法。

使用 `<where>` 后，MyBatis 会自动处理这类问题。

典型写法：

```xml
<select id="list" resultType="com.itheima.pojo.Emp">
    select e.*, d.name as deptName
    from emp e
    left join dept d on e.dept_id = d.id
    <where>
        <if test="name != null and name != ''">
            e.name like concat('%', #{name}, '%')
        </if>
        <if test="gender != null">
            and e.gender = #{gender}
        </if>
        <if test="begin != null and end != null">
            and e.entry_date between #{begin} and #{end}
        </if>
    </where>
    order by e.update_time desc
</select>
```

一句话理解：

> `<where>` 负责生成完整条件区块，并自动清理多余的前导 `and` / `or`。

### 11. 这一阶段的总结

条件分页查询优化这一阶段，核心完成了三件事：

1. 把多个查询参数封装成 `EmpQueryParam`
2. 在 `EmpMapper.xml` 中使用动态 SQL
3. 通过 `<if>` 和 `<where>` 根据参数是否为空动态拼接查询条件

一句话总结：

> 条件分页查询的本质是在原有分页能力基础上，引入参数对象和动态 SQL，让查询条件既能动态传值，也能动态决定是否参与查询。

## 七、新增员工

### 1. 新增员工的整体思路

新增员工这一阶段，整体上会同时涉及三部分数据：

1. 员工基本信息，保存到 `emp` 表
2. 员工工作经历信息，保存到 `emp_expr` 表
3. 员工头像，图片文件上传到 OSS，数据库中通常保存图片地址

一句话理解：

> 新增员工不是只插一张表，而是同时涉及主表、子表和图片地址，因此后面自然会引出事务管理和文件上传。

### 2. 新增员工接口的请求体结构

前端提交的是一个复合 JSON，请求体中既有员工基本信息，也有工作经历列表。

可以先理解成两层：

- 外层：员工主信息
- `exprList`：员工工作经历列表

其中：

- 员工主信息对应 `emp` 表
- 工作经历列表对应 `emp_expr` 表
- `image` 字段通常是图片先上传到 OSS 后得到的访问地址

### 3. 为了接收 `exprList`，需要扩展 `Emp`

由于前端提交的新增员工请求体中包含：

```json
"exprList": [ ... ]
```

所以为了让后端一次性接住整个 JSON，课程里会在 `Emp` 实体类中增加：

```java
private List<EmpExpr> exprList;
```

说明：

- 这里的 `Emp` 不只是映射 `emp` 表字段
- 还临时承担了新增员工请求对象的角色

更规范的项目中，也可以单独定义 DTO 或参数对象来接收这类复合请求体。

### 4. Controller 层职责

新增员工接口中，前端传的是 JSON 请求体，因此 Controller 需要使用：

```java
@RequestBody
```

来接收参数。

典型写法：

```java
@PostMapping
public Result save(@RequestBody Emp emp) {
    log.info("请求参数emp: {}", emp);
    empService.save(emp);
    return Result.success();
}
```

Controller 的职责：

1. 接收请求体
2. 调用 `empService.save(emp)`
3. 返回统一结果

一句话理解：

> Controller 负责接收新增员工的 JSON 请求体，再把数据交给 Service 处理。

### 5. Service 层职责

`EmpServiceImpl` 中的 `save` 方法负责组织新增员工的完整业务流程。

第一步先做员工主表保存：

```java
public void save(Emp emp) {
    emp.setCreateTime(LocalDateTime.now());
    emp.setUpdateTime(LocalDateTime.now());

    empMapper.insert(emp);
}
```

这里的关键点：

- 在 Service 层补 `createTime` 和 `updateTime`
- 先保存员工基本信息到 `emp` 表

一句话理解：

> Service 先补全基础字段，再调用 Mapper 保存员工主表数据。

### 6. Mapper 层保存员工基本信息

Mapper 中先定义主表插入方法：

```java
void insert(Emp emp);
```

再通过 `insert into emp (...) values (...)` 保存员工基本信息。

说明：

- 数据库字段仍然是下划线命名
- Java 属性仍然是小驼峰命名

例如：

```text
entry_date <- entryDate
dept_id <- deptId
create_time <- createTime
update_time <- updateTime
```

### 7. 主键回填

插入 `emp` 主表后，后续还要把工作经历写入 `emp_expr`，因此必须先拿到新员工的主键 `id`。

在 MyBatis 中，可以通过：

```java
@Options(useGeneratedKeys = true, keyProperty = "id")
```

实现主键回填。

典型写法：

```java
@Options(useGeneratedKeys = true, keyProperty = "id")
@Insert("insert into emp(...) values(...)")
void insert(Emp emp);
```

这样在执行：

```java
empMapper.insert(emp);
```

之后，就可以直接通过：

```java
emp.getId()
```

拿到数据库生成的员工主键。

一句话理解：

> 通过 `@Options(useGeneratedKeys = true, keyProperty = "id")`，可以让 MyBatis 在插入 `emp` 后自动把主键回填到 `emp.id`。

### 8. 保存工作经历信息

员工基本信息保存完成后，下一步是保存工作经历列表。

这一步的核心流程是：

1. 先拿到新员工的 `id`
2. 遍历 `exprList`
3. 给每条工作经历补上员工 `id`
4. 批量插入 `emp_expr`

一句话理解：

> 保存工作经历前，必须先拿到员工主键，再让每条工作经历和该员工建立关联。

### 9. 插入工作经历前先判断列表是否为空

在真正保存工作经历前，通常会先做判断：

```java
CollectionUtils.isEmpty(emp.getExprList())
```

只有当 `exprList` 不为空时，才继续执行：

- 补员工 `id`
- 批量插入工作经历

这样做的好处：

- 避免空指针
- 避免无意义的批量插入

### 10. 批量插入工作经历使用 `<foreach>`

工作经历条数不固定，因此这里也需要使用动态 SQL。

不过这一块的动态 SQL 不是 `<if>` / `<where>`，而是：

```xml
<foreach>
```

Mapper 接口示例：

```java
public void insertBatch(List<EmpExpr> exprList);
```

XML 典型写法：

```xml
<insert id="insertBatch">
    insert into emp_expr (emp_id, begin, end, company, job) values
    <foreach collection="exprList" item="expr" separator=",">
        (#{expr.empId}, #{expr.begin}, #{expr.end}, #{expr.company}, #{expr.job})
    </foreach>
</insert>
```

`<foreach>` 常见属性说明：

- `collection`：集合名
- `item`：每次遍历出的元素名
- `separator`：每组数据之间的分隔符
- `open`：遍历开始前拼接的片段
- `close`：遍历结束后拼接的片段

一句话理解：

> `<foreach>` 用来把 `List<EmpExpr>` 动态展开成多组 `values (...)`，从而实现 `emp_expr` 的批量插入。

### 11. 新增员工这一阶段的三层职责

#### Controller

- 接收新增员工请求体
- 调用 Service
- 返回统一结果

#### Service

- 补时间字段
- 保存 `emp` 主表
- 判断 `exprList` 是否为空
- 给工作经历补员工 `id`
- 批量保存 `emp_expr`

#### Mapper

- 执行 `insert into emp (...) values (...)`
- 执行 `insert into emp_expr (...) values (...), (...), ...`

一句话总结：

> 新增员工的本质是：Controller 接收复合请求体，Service 组织主表新增和子表批量新增，Mapper 执行两类插入 SQL。

## 八、事务管理

### 1. 事务概览

事务是一组操作的集合，是一个不可分割的工作单位。

事务会把所有操作作为一个整体一起向系统提交或撤销操作请求，也就是说：

- 要么全部成功
- 要么全部失败

一句话理解：

> 事务的核心作用，就是防止一组相关操作只成功一半。

### 2. 结合新增员工理解事务

在新增员工场景中，至少会涉及两类数据库操作：

1. 插入 `emp` 主表
2. 批量插入 `emp_expr` 工作经历表

如果：

- `emp` 插入成功
- `emp_expr` 插入失败

那么数据库中就会只留下员工主信息，而没有对应工作经历，数据会变得不完整。

因此，新增员工这组操作必须放在同一个事务中处理：

- 都成功，事务提交
- 其中一步失败，事务回滚

一句话总结：

> 在新增员工中，保存员工主表和保存工作经历必须放在同一个事务里，要么一起成功，要么一起失败。

### 3. 事务控制的三步操作

事务控制的核心操作可以概括成三步：

1. 开启事务
2. 提交事务
3. 回滚事务

原始 SQL 角度可以理解成：

```sql
start transaction;
-- 执行业务 SQL
commit;
-- 或 rollback;
```

说明：

- 所有业务 SQL 都成功时，执行 `commit`
- 中间任意一步失败时，执行 `rollback`

一句话理解：

> 事务控制就是先把多条 SQL 绑定成一个整体，再根据执行结果决定统一提交还是统一回滚。

### 4. Spring 事务管理

在 Spring 中，通常不需要手动写：

```sql
start transaction;
commit;
rollback;
```

而是通过注解：

```java
@Transactional
```

把当前业务方法交给 Spring 管理事务。

Spring 会自动完成：

1. 方法执行前开启事务
2. 方法正常执行结束时提交事务
3. 方法执行过程中出现异常时回滚事务

一句话理解：

> `@Transactional` 本质上就是把“开启事务、提交事务、回滚事务”交给 Spring 自动处理。

### 5. `@Transactional` 的位置

事务注解通常放在业务层（Service）中。

可以加在：

- 方法上
- 类上
- 接口上

当前学习阶段最推荐、也最直观的用法是：

```java
@Transactional
@Override
public void save(Emp emp) {
    ...
}
```

说明：

- 加在方法上，作用范围最明确
- 当前新增员工场景中，`save(Emp emp)` 正好负责组织主表新增和子表批量新增

### 6. 为什么图里会故意制造异常

课程里通常会在 `save()` 方法中故意写类似：

```java
int i = 1 / 0;
```

目的是测试事务是否生效。

如果没有事务：

- `emp` 插入成功后会立刻生效
- 后面报错时，前面的主表数据不会自动撤回

如果有 `@Transactional`：

- `emp` 插入后虽然先执行了
- 但后面出现异常时，整个方法会回滚
- 前面已经插入的 `emp` 数据也会被撤销

一句话理解：

> 通过故意制造异常，可以验证事务是否真的实现了“要么一起成功，要么一起失败”。

### 7. 新增员工场景下的事务落点

在新增员工中，事务最适合加在：

```java
EmpServiceImpl.save(Emp emp)
```

因为这个方法负责组织一整组相关操作：

1. 插入 `emp`
2. 主键回填
3. 给 `exprList` 补 `empId`
4. 批量插入 `emp_expr`

所以当前最适合的理解是：

> 事务控制的对象不是某一条 SQL，而是 `save(Emp emp)` 这整个业务方法。

### 8. `rollbackFor` 的作用

`@Transactional` 默认情况下：

- 遇到 `RuntimeException` 会回滚
- 遇到 `Error` 会回滚
- 对于普通编译时异常 `Exception`，默认不一定回滚

如果希望某些其他异常类型出现时也回滚事务，可以使用：

```java
@Transactional(rollbackFor = Exception.class)
```

它的意思是：

> 当方法中抛出 `Exception` 及其子类异常时，也要回滚事务。

一句话理解：

> `rollbackFor` 用来指定“出现哪些异常类型时，事务需要回滚”。

### 8.1 事务日志配置

为了更直观看到 Spring 是否真正开启、提交或回滚了事务，可以在 `application.yml` 中增加事务日志配置：

```yaml
logging:
  level:
    org.springframework.jdbc.support.JdbcTransactionManager: debug
```

作用：

- 观察事务是否开启
- 观察事务是否提交
- 观察异常时是否发生回滚

一句话理解：

> 配置事务日志不是为了让事务生效，而是为了更容易验证事务有没有生效。

### 9. 事务传播行为 `propagation`

事务传播行为指的是：

> 当一个事务方法调用另一个事务方法时，被调用方法应该如何参与当前事务。

也就是说，它解决的问题不是“回不回滚”，而是：

> 两个事务方法嵌套调用时，后一个方法该加入当前事务，还是新开一个事务。

### 10. 重点关注 `REQUIRED` 和 `REQUIRES_NEW`

#### `Propagation.REQUIRED`

这是默认值，也是最常用的传播行为。

含义：

- 当前有事务：加入当前事务
- 当前没有事务：新建一个事务

一句话理解：

> 有事务就加入，没有事务就新建。

它适合“本来就是同一件业务”的场景。

例如新增员工时：

- 保存员工主信息
- 保存工作经历

这两个动作通常希望在同一个事务里一起成功、一起失败，所以很适合 `REQUIRED`。

#### `Propagation.REQUIRES_NEW`

含义：

- 无论当前是否存在事务，都新建一个事务

如果外层已经有事务，则外层事务会先被挂起，等当前新事务执行完后，再恢复外层事务。

一句话理解：

> 不跟外层共用事务，我单独开一个。

它适合“希望独立提交或独立回滚”的子业务场景。

### 11. 用“新增员工 + 记录日志”理解 `REQUIRES_NEW`

需求：

> 在新增员工信息时，无论成功还是失败，都要记录操作日志。

如果“记录日志”方法使用的是 `REQUIRED`：

- 日志和新增员工主业务共用同一个事务
- 如果主业务失败回滚，日志也会一起回滚

这样就达不到“无论成功还是失败都要记录日志”的目的。

如果“记录日志”方法使用的是：

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
```

那么日志方法会单独开启一个事务。

这意味着：

- 日志可以先独立提交
- 即使后面新增员工主业务失败回滚
- 已经提交成功的日志仍然可以保留下来

一句话总结：

> `REQUIRED` 适合主业务整体成败，`REQUIRES_NEW` 适合需要独立提交或独立回滚的子业务，例如操作日志记录。

### 12. 事务的四大特性（ACID）

#### 原子性 Atomicity

事务是不可分割的最小单位。

意思是：

> 事务中的操作要么全部成功，要么全部失败。

在新增员工中：

- 插入 `emp`
- 插入 `emp_expr`

不能只成功一半。

#### 一致性 Consistency

事务执行前后，数据库都要保持正确、一致的状态。

在新增员工中：

- 员工主信息和工作经历的关联要完整
- 不能出现主表有了、子表残了的情况

#### 隔离性 Isolation

多个事务并发执行时，彼此之间应该尽量互不干扰。

当前阶段可以先理解成：

> 一个事务执行时，尽量不要被其他并发事务影响。

#### 持久性 Durability

事务结果一旦确定，就会永久生效。

也就是说：

- 提交成功后，数据会真正落库
- 回滚完成后，撤销结果也会真正生效

一句话总结：

> ACID 分别表示：原子性、 一致性、隔离性、持久性；在新增员工场景里，原子性最直观，而一致性、隔离性、持久性共同保证事务结果正确、稳定且可长期保存。

## 九、文件上传

### 1. 文件上传简介

文件上传，指的是将本地的图片、视频、音频等文件上传到服务器或云存储中，供其他用户浏览、下载或后续业务使用的过程。

在当前员工管理场景中，文件上传通常对应的是员工头像上传：

1. 前端选择图片文件
2. 后端接收文件
3. 将文件保存到本地或上传到 OSS
4. 返回图片访问地址
5. 再把这个地址保存到员工信息的 `image` 字段中

一句话理解：

> 文件上传的本质，是先把文件保存到合适的位置，再把访问地址或路径用于后续业务。

### 2. 文件上传的后端接收方式

后端接收上传文件时，核心是使用：

```java
MultipartFile
```

例如：

```java
@PostMapping("/upload")
public Result handleFileUpload(String name, Integer age, MultipartFile file) {
    log.info("文件上传:{}", file);
    return Result.success();
}
```

说明：

- 普通表单字段仍然按普通参数接收
- 文件字段通过 `MultipartFile` 接收
- 前端文件输入框的 `name` 属性，需要和后端 `MultipartFile` 参数名保持一致

一句话理解：

> 文件上传在后端的核心处理方式，就是通过 `MultipartFile` 参数接收前端上传的文件。

### 3. 本地存储的基本流程

当前阶段文件上传先学习本地存储方案，核心流程是：

1. 获取原始文件名
2. 生成新的唯一文件名
3. 保存文件到本地目录

#### 获取原始文件名

```java
String originalFilename = file.getOriginalFilename();
```

作用：

- 获取用户上传文件时的原始名字
- 后续通常基于它提取文件后缀

#### 生成新的唯一文件名

由于不同客户端可能上传相同原始文件名的文件，如果直接使用原文件名保存，容易发生覆盖。

所以通常会：

1. 截取原文件后缀
2. 使用 UUID 生成新的唯一文件名

例如：

```java
String extname = originalFilename.substring(originalFilename.lastIndexOf("."));
String newFilename = UUID.randomUUID().toString() + extname;
```

说明：

- `UUID.randomUUID()` 用来生成随机唯一标识
- 原文件后缀保留下来，方便维持文件类型

一句话理解：

> 原始文件名只用于提取后缀，真正存储时通常使用 `UUID + 后缀` 生成唯一文件名，避免同名覆盖。

#### 保存文件

通过：

```java
file.transferTo(...)
```

可以把上传到后端的文件保存到目标位置。

例如：

```java
file.transferTo(new File("目标路径/" + newFilename));
```

一句话理解：

> `file.transferTo()` 的作用，就是把上传到后端的文件真正转存到指定位置。

### 4. 文件上传大小限制

Spring Boot 默认对上传文件大小有限制，常见默认值可以先理解为：

- 单个文件最大 `1MB`
- 单次请求总大小最大 `10MB`

如果需要调整，可以通过配置项修改：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 10MB
```

说明：

- `max-file-size`：单个文件最大大小
- `max-request-size`：一次请求总大小

一句话理解：

> 文件上传大小限制可以通过 `spring.servlet.multipart.*` 配置项调整。

### 5. 本地存储阶段小结

本地存储阶段，重点先掌握这条主线：

1. `MultipartFile` 接收文件
2. `getOriginalFilename()` 获取原始文件名
3. 取后缀并用 `UUID.randomUUID()` 生成唯一文件名
4. `transferTo()` 保存文件
5. 必要时通过配置项调整上传大小限制

一句话总结：

> 本地文件上传的核心流程就是：接收文件、生成唯一文件名、保存文件，并根据需要调整上传大小限制。

### 6. 接入第三方服务的通用思路

在接入阿里云 OSS 之前，先记住第三方服务的一般套路：

1. 准备工作
2. 参照官方 SDK 编写入门程序
3. 集成到当前项目中使用

一句话理解：

> 接第三方服务时，先准备服务与权限，再跑通官方最小示例，最后再融入业务项目。

### 7. 阿里云 OSS 使用步骤

当前课程里，OSS 的主线可以压成：

1. 开通 OSS
2. 创建 Bucket
3. 获取并配置 AccessKey
4. 参考官方 SDK 编写入门程序
5. 案例集成 OSS

说明：

- Bucket 可以先理解为 OSS 中的“存储桶/文件仓库”
- AccessKey 可以理解为程序访问 OSS 的凭证
- 获取到 AccessKey 后，通常先配置环境变量，再由代码读取使用，避免把密钥直接写死在源码中

一句话理解：

> OSS 接入的顺序是：先准备服务、存储空间和密钥，再参考官方 SDK 跑通示例，最后集成到项目里。

### 8. 案例集成 OSS

案例集成 OSS 时，文件上传的链路会变成：

1. 前端选择头像文件
2. 调用后端上传接口
3. 后端通过 `MultipartFile` 接收文件
4. 后端调用 OSS 上传工具类把文件传到阿里云 OSS
5. OSS 返回或拼出文件访问 URL
6. 后端把 URL 返回给前端
7. 前端再把这个 URL 放进新增员工请求里的 `image`

一句话理解：

> 上传接口不再把文件保存到本地，而是上传到 OSS，再把图片访问 URL 返回给前端。

### 9. OSS 上传工具类

课程中先参考阿里云 OSS 官方 Demo，再改造成项目里的工具类，例如：

- `endpoint`
- `bucketName`
- `region`
- 从环境变量读取 `OSS_ACCESS_KEY_ID` 和 `OSS_ACCESS_KEY_SECRET`

工具类的核心职责是：

1. 接收文件内容和文件名
2. 生成 OSS 中的对象路径 `objectName`
3. 创建 OSSClient
4. 调用 `putObject(...)` 上传文件
5. 返回文件访问 URL

其中 `objectName` 通常会这样生成：

1. 按日期生成目录，例如 `yyyy/MM`
2. 取原文件后缀
3. 使用 UUID 生成唯一文件名
4. 最终拼成 `目录/文件名`

例如：

```java
String dir = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM"));
String newFileName = UUID.randomUUID() + originalFilename.substring(originalFilename.lastIndexOf("."));
String objectName = dir + "/" + newFileName;
```

一句话理解：

> OSS 工具类负责把文件内容上传到指定 Bucket，并返回文件访问地址给业务层使用。

### 10. UploadController 在 OSS 场景下的职责

案例集成后，`UploadController` 的职责是：

1. 接收前端上传的 `MultipartFile`
2. 调用 `AliyunOSSOperator`
3. 拿到上传成功后的 URL
4. 把 URL 返回给前端

例如控制器层的主线是：

```java
@PostMapping("/upload")
public Result upload(MultipartFile file) throws Exception {
    String url = aliyunOSSOperator.upload(file.getBytes(), file.getOriginalFilename());
    return Result.success(url);
}
```

说明：

- Controller 负责接文件和返回结果
- OSS 上传细节交给工具类处理
- 返回给前端的不是文件本身，而是图片访问 URL

一句话理解：

> Controller 在 OSS 场景下的任务是接文件、调工具类上传 OSS、把图片 URL 回给前端。

### 11. 外部化 OSS 配置

为了避免把 OSS 的固定参数直接写死在工具类里，可以先把配置放到 `application.yml` 中，例如：

```yaml
aliyun:
  oss:
    endpoint: https://oss-cn-beijing.aliyuncs.com
    bucketName: java-ai
    region: cn-beijing
```

#### 使用 `@Value`

当配置项不多时，可以在工具类中使用：

```java
@Value("${aliyun.oss.endpoint}")
private String endpoint;

@Value("${aliyun.oss.bucketName}")
private String bucketName;

@Value("${aliyun.oss.region}")
private String region;
```

作用：

- 从 `application.yml` 中读取配置
- 避免把 endpoint、bucketName、region 硬编码在 Java 代码里

一句话理解：

> `@Value` 适合读取少量单个配置项，但配置一多会显得比较零散。

#### 使用 `@ConfigurationProperties`

当同一模块下的配置项较多时，Spring 更推荐使用批量绑定：

```java
@Component
@ConfigurationProperties(prefix = "aliyun.oss")
public class AliyunOSSProperties {
    private String endpoint;
    private String bucketName;
    private String region;

    // getter / setter
}
```

说明：

1. 配置类中的属性名，需要和配置项最后一级名字保持一致
2. 配置类需要交给 Spring IOC 容器管理
3. 通过 `@ConfigurationProperties(prefix = "aliyun.oss")` 指定配置前缀

一句话理解：

> `@ConfigurationProperties` 更适合把同一前缀下的一组配置批量绑定到一个配置类中，适用于配置较多的场景。

### 12. 一个值得注意的小细节

课程代码里，Controller 先生成一次唯一文件名，再把这个名字传进 OSS 工具类；而工具类内部又会基于后缀再次生成新的 UUID 文件名。

这种写法可以运行，但有一点重复。

更清晰的职责划分通常有两种：

1. Controller 直接传原始文件名，工具类统一负责生成最终 OSS 文件名
2. Controller 生成好唯一文件名，工具类直接使用，不再二次生成

当前学习阶段，更推荐第一种理解方式：

> Controller 负责接文件，OSS 工具类统一负责生成最终对象名并上传。

### 13. OSS 阶段小结

当前 OSS 阶段先抓住这条主线：

1. 开通 OSS、创建 Bucket、配置 AccessKey
2. 参考官方 SDK 跑通最小上传示例
3. 在项目中封装 `AliyunOSSOperator`
4. 通过上传接口接收文件并上传到 OSS
5. 返回图片 URL 给前端
6. 前端再把 URL 用于新增员工的 `image`

一句话总结：

> OSS 集成的核心不是“把文件传出去”这么简单，而是把上传能力封装进项目，并让新增员工最终保存的是图片 URL 而不是本地文件。

## 十、删除员工

### 1. 删除功能的整体思路

删除员工不是单表删除，而是一个组合删除过程：

1. 删除员工工作经历表 `emp_expr` 中对应员工的记录
2. 删除员工主表 `emp` 中对应员工的记录

一句话理解：

> 删除员工时，通常要先删子表 `emp_expr`，再删主表 `emp`，这样数据更完整，也更符合外键依赖方向。

### 2. 删除功能涉及的 SQL

#### 删除员工主表

```sql
DELETE FROM emp
WHERE id IN (1, 2, 3);
```

作用：

- 根据多个员工 id 批量删除员工主表记录

#### 删除员工工作经历表

```sql
DELETE FROM emp_expr
WHERE emp_id IN (1, 2, 3);
```

作用：

- 根据多个员工 id 批量删除 `emp_expr` 中对应的工作经历记录

说明：

- `emp` 表按 `id` 删除
- `emp_expr` 表按 `emp_id` 删除，因为它通过 `emp_id` 关联员工主表

一句话理解：

> 删除员工功能本质上是“先按 `emp_id` 删工作经历，再按 `id` 删员工主表”的两步操作。

### 3. 删除功能的三层架构职责

#### Controller

1. 接收请求参数 `ids`
2. 调用 Service 方法
3. 返回结果

#### Service

1. 组织完整删除业务
2. 先删除 `emp_expr`
3. 再删除 `emp`

#### Mapper

1. 执行 `emp_expr` 删除 SQL
2. 执行 `emp` 删除 SQL

一句话理解：

> Controller 负责接参数，Service 负责组织“先删子表、再删主表”的业务顺序，Mapper 负责真正执行批量删除 SQL。

### 4. Controller 接收删除参数

前端通常通过这种方式传递多个员工 id：

```text
DELETE /emps?ids=1,2,3
```

后端在 Controller 中有两种常见接收方式。

#### 方式一：数组接收

```java
@DeleteMapping
public Result delete(Integer[] ids) {
    return Result.success();
}
```

#### 方式二：集合接收

```java
@DeleteMapping
public Result delete(@RequestParam List<Integer> ids) {
    return Result.success();
}
```

说明：

- 数组和集合两种方式都可以
- 当使用 `List<Integer>` 接收时，通常配合 `@RequestParam` 更稳
- 当前学习阶段更推荐记 `List<Integer> ids` 这种方式，因为后面在 Service / Mapper 中更顺手

一句话理解：

> 删除员工时，前端通常通过 `DELETE /emps?ids=1,2,3` 传递多个 id，Controller 中既可以用数组接收，也可以用 `@RequestParam List<Integer>` 接收。

### 5. Service 层删除实现

删除员工在 Service 层中，本质上是一个“组合删除业务”，因此需要放在同一个事务里统一控制。

例如：

```java
@Transactional(rollbackFor = Exception.class)
@Override
public void delete(List<Integer> ids) {
    empMapper.deleteByIds(ids);
    empExprMapper.deleteByEmpIds(ids);
}
```

说明：

1. `delete(List<Integer> ids)` 不是只转发一条 SQL，而是组织多条删除操作
2. `@Transactional(rollbackFor = Exception.class)` 用来保证删除主表和子表时要么一起成功，要么一起失败
3. `rollbackFor = Exception.class` 表示除了默认运行时异常外，普通 `Exception` 也会触发事务回滚

一句话理解：

> 删除员工功能在 Service 层通过事务统一包住 emp 和 emp_expr 的删除操作，避免删除过程只成功一半。

### 6. 关于删除顺序的提醒

从更稳妥的业务顺序看，通常更推荐：

1. 先删除 `emp_expr`
2. 再删除 `emp`

原因：

- `emp_expr` 是子表
- `emp` 是主表
- 如果数据库存在外键依赖，先删主表可能会失败

课程代码中如果出现“先删主表、再删子表”的写法，在没有外键约束的教学环境里可能也能运行；但从关系型数据库设计和更稳妥的删除逻辑看，通常更推荐“先删子表，再删主表”。

### 7. Mapper XML 中的批量删除

由于删除员工时传入的是一组 `ids`，而 `ids` 个数不固定，所以批量删除通常放在 XML 中，使用 `<foreach>` 动态拼接 `IN (...)`。

#### 删除员工主表

```xml
<delete id="deleteByIds">
    delete from emp where id in
    <foreach collection="ids" item="id" separator="," open="(" close=")">
        #{id}
    </foreach>
</delete>
```

说明：

- `collection="ids"`：要遍历的集合参数名
- `item="id"`：每次遍历出的单个员工 id
- `separator=","`：多个 id 之间用逗号隔开
- `open="("`、`close=")"`：在遍历前后补上括号

最终效果类似：

```sql
delete from emp where id in (1,2,3)
```

#### 删除员工工作经历表

```xml
<delete id="deleteByEmpIds">
    delete from emp_expr where emp_id in
    <foreach collection="empIds" item="empId" separator="," open="(" close=")">
        #{empId}
    </foreach>
</delete>
```

说明：

- 这里删除的是 `emp_expr` 表中的记录
- 由于 `emp_expr` 通过 `emp_id` 关联员工主表，所以这里按 `emp_id in (...)` 批量删除
- `empIds` 表示传入的员工 id 集合，`empId` 表示每次遍历的单个员工 id

一句话理解：

> 删除功能里的动态 SQL 重点不是 `<if>`，而是通过 `<foreach>` 动态生成 `IN (...)` 中的参数列表。

## 十一、修改员工前的查询回显

### 1. 查询回显的目标

修改员工时，前端点击“编辑”后，需要先把该员工当前已有的数据查出来，再回填到表单中。

回显的数据仍然分成两块：

1. 员工基本信息（表：`emp`）
2. 员工工作经历信息（表：`emp_expr`）

一句话理解：

> 查询回显的本质是：根据员工 id 查询员工完整详情数据，并把主表信息和工作经历列表一起返回给前端做表单回填。

### 2. 查询回显的三层职责

#### Controller

1. 接收请求参数（员工 id）
2. 调用 Service 方法
3. 响应结果

#### Service

1. 调用 Mapper 查询员工完整信息
2. 获取员工基本信息和工作经历信息
3. 返回给 Controller

#### Mapper

1. 编写联表查询 SQL
2. 根据员工 id 查询员工主表与工作经历表数据

一句话理解：

> 查询回显时，Controller 负责接 id，Service 负责组织查询，Mapper 负责通过联表 SQL 一次查出员工基本信息和工作经历信息。

### 3. 联表查询 SQL

查询回显时，可以先通过 `emp` 和 `emp_expr` 做左外连接，根据员工 `id` 查询员工主信息及其工作经历。

例如：

```sql
SELECT
    e.*,
    ee.id eeid,
    ee.emp_id ee_empid,
    ee.begin ee_begin,
    ee.end ee_end,
    ee.company ee_company,
    ee.job ee_job
FROM emp e
LEFT JOIN emp_expr ee
ON e.id = ee.emp_id
WHERE e.id = 59;
```

说明：

- 使用 `LEFT JOIN`，可以保证即使员工没有工作经历，也能把员工主信息查出来
- `e.*` 表示员工主表字段
- `ee.xxx` 都起了别名，用于区分工作经历表字段，避免和主表字段重名

一句话理解：

> 查询回显时，通常通过 `emp` 和 `emp_expr` 左连接查询，并对工作经历表字段起别名，以方便后续结果映射。

### 4. Controller / Service / Mapper 实现

#### Controller

查询回显接口通常按员工 id 查询，常见写法：

```java
@GetMapping("/{id}")
public Result getInfo(@PathVariable Integer id) {
    log.info("根据ID查询员工信息：{}", id);
    Emp emp = empService.getInfo(id);
    return Result.success(emp);
}
```

说明：

- `@GetMapping("/{id}")` 表示按路径参数接收员工 id
- `@PathVariable` 用来接收 URL 中的 `{id}`
- Controller 只负责接 id、调 Service、回结果

#### Service

Service 层通常只是把“根据 id 查询员工信息”这件事串起来：

```java
@Override
public Emp getInfo(Integer id) {
    return empMapper.getById(id);
}
```

说明：

- 当前阶段 Service 层主要做查询转发
- 真正的数据查询细节在 Mapper 中完成

#### Mapper

Mapper 接口方法通常会写成：

```java
Emp getById(Integer id);
```

对应 XML：

```xml
<select id="getById" resultType="com.itheima.pojo.Emp">
    select
        e.*,
        ee.id ee_id,
        ee.emp_id ee_empid,
        ee.begin ee_begin,
        ee.end ee_end,
        ee.company ee_company,
        ee.job ee_job
    from emp e left join emp_expr ee on e.id = ee.emp_id
    where e.id = #{id}
</select>
```

说明：

- `#{id}` 动态接收传入的员工 id
- 通过左连接一次把员工主信息和工作经历相关字段查出来
- `ee` 相关字段起别名，是为了和主表字段区分开，便于后续映射或封装

一句话理解：

> 查询回显当前阶段的实现链路是：Controller 接路径参数 id，Service 调用 `empMapper.getById(id)`，Mapper 通过左连接 SQL 一次查出员工主表和工作经历相关字段。

### 5. 一个值得注意的小点

从当前截图看，Mapper 已经把联表查询打通了；但如果后续目标是把工作经历真正封装成：

```java
Emp {
    ...
    List<EmpExpr> exprList;
}
```

那么通常还需要进一步处理结果映射，例如继续补 `resultMap` 或做后续封装。

当前先记住主线即可：

> 先把“根据 id 查询员工完整信息”这条通路打通，再继续处理回显结果的细节映射。

### 6. 为什么自动结果封装不够

如果只写：

```xml
<select id="getById" resultType="com.itheima.pojo.Emp">
```

MyBatis 默认只能比较自然地把查询结果封装到 `Emp` 的普通属性里，例如：

- `id`
- `username`
- `name`
- `gender`
- `entryDate`

但当前查询回显不是只有主表字段，还包含了：

- 员工主信息
- 工作经历列表 `exprList`

这里的难点在于：

> 联表查询返回的是“多行结果”，而最终想要的是“一个 `Emp` 对象 + 一个 `List<EmpExpr>`”。

自动结果封装对这种嵌套集合场景支持不够，所以需要自定义结果映射。

一句话理解：

> 自动封装适合普通字段，不适合“一个对象里再套一个集合”的联表结果。

### 7. 自定义结果映射 `resultMap`

这时通常要在 XML 中定义：

```xml
<resultMap id="empResultMap" type="com.itheima.pojo.Emp">
    <id column="id" property="id" />
    <result column="username" property="username" />
    <result column="password" property="password" />
    <result column="name" property="name" />
    <result column="gender" property="gender" />
    <result column="image" property="image" />
    <result column="entry_date" property="entryDate" />
    <result column="dept_id" property="deptId" />
    <result column="create_time" property="createTime" />
    <result column="update_time" property="updateTime" />

    <collection property="exprList" ofType="com.itheima.pojo.EmpExpr">
        <id column="ee_id" property="id" />
        <result column="ee_company" property="company" />
        <result column="ee_job" property="job" />
        <result column="ee_begin" property="begin" />
        <result column="ee_end" property="end" />
        <result column="ee_empid" property="empId" />
    </collection>
</resultMap>
```

然后把查询语句改成：

```xml
<select id="getById" resultMap="empResultMap">
```

说明：

- `resultMap` 负责把主表字段映射到 `Emp`
- `<collection>` 负责把工作经历相关字段映射到 `exprList`
- `ofType="com.itheima.pojo.EmpExpr"` 表示集合中每个元素的类型

一句话理解：

> `resultMap` 解决的是“主对象字段怎么映射”，`<collection>` 解决的是“子表多行数据怎么封装成集合”。

### 8. 当前这一步的核心收获

查询回显之所以要自定义结果封装，不是因为 SQL 不对，而是因为：

1. 联表结果是多行
2. 目标对象是 `Emp + List<EmpExpr>`
3. 自动封装难以直接处理这种嵌套集合结构

所以这里真正的重点是：

> 当查询结果需要封装成“一个对象 + 一个集合”时，通常要使用 MyBatis 的 `resultMap + collection` 自定义结果映射。

### 9. `resultType` 和 `resultMap` 的使用判断

#### 使用 `resultType`

当查询返回的字段名和实体类属性名可以直接对应上，且结果结构比较简单时，通常使用：

```xml
resultType
```

适合场景：

- 普通单表查询
- 结果字段和实体属性能自然映射
- 不涉及复杂嵌套结构

#### 使用 `resultMap`

当出现以下情况时，更适合使用：

```xml
resultMap
```

1. 查询返回字段名和实体类属性名不能直接对应
2. 查询结果结构较复杂
3. 需要手动控制字段映射关系
4. 存在嵌套对象或集合映射

在当前员工查询回显场景中，由于最终要封装成：

```java
Emp + List<EmpExpr>
```

所以更适合使用 `resultMap + collection`。

一句话理解：

> 简单映射用 `resultType`，复杂映射用 `resultMap`。

## 十二、修改员工

### 1. 修改功能的核心思路

修改员工时，后端处理的核心是两部分：

1. 修改员工主表 `emp` 中的基本信息
2. 修改工作经历表 `emp_expr` 中的经历列表

其中工作经历通常采用：

> 先删除旧记录，再批量插入新记录

一句话理解：

> 修改员工的本质是：更新主表信息，并用“先删后插”的方式更新工作经历列表。

### 2. 修改功能的三层职责

#### Controller

1. 接收前端传来的完整员工对象
2. 调用 Service 方法
3. 返回结果

#### Service

1. 更新员工主表信息
2. 删除旧工作经历
3. 批量插入新工作经历
4. 用事务统一控制整组更新操作

#### Mapper

1. `update emp set ...`
2. `delete from emp_expr where emp_id in (...)`
3. `insert into emp_expr ...`

一句话理解：

> Controller 负责接请求，Service 负责组织“更新主表 + 删除旧经历 + 重新插入新经历”，Mapper 负责真正执行更新和删除新增 SQL。

### 3. Controller 实现

修改接口通常使用：

```java
@PutMapping
public Result update(@RequestBody Emp emp) {
    log.info("修改员工：{}", emp);
    empService.update(emp);
    return Result.success();
}
```

说明：

- 使用 `@PutMapping` 表示修改操作
- 使用 `@RequestBody Emp emp` 接收前端传来的完整员工对象
- Controller 只负责接参数、调 Service、回结果

一句话理解：

> 修改员工接口通常通过 `@PutMapping + @RequestBody` 接收完整员工数据，再交给 Service 完成更新。

### 4. Service 实现

Service 层的核心代码通常类似：

```java
@Transactional(rollbackFor = Exception.class)
@Override
public void update(Emp emp) {
    // 1. 根据ID修改员工基本信息
    emp.setUpdateTime(LocalDateTime.now());
    empMapper.updateById(emp);

    // 2. 根据ID修改员工工作经历信息
    // 2.1 先根据员工ID删除原有工作经历
    empExprMapper.deleteByEmpIds(Arrays.asList(emp.getId()));

    // 2.2 再添加这个员工新的工作经历
    List<EmpExpr> exprList = emp.getExprList();
    if (!CollectionUtils.isEmpty(exprList)) {
        exprList.forEach(empExpr -> empExpr.setEmpId(emp.getId()));
        empExprMapper.insertBatch(exprList);
    }
}
```

说明：

1. 先给员工对象补 `updateTime`
2. 调用 `empMapper.updateById(emp)` 更新主表
3. 再根据员工 `id` 删除原有工作经历
4. 最后把新的 `exprList` 重新批量插入

这里的：

```java
Arrays.asList(emp.getId())
```

是因为前面的 `deleteByEmpIds(...)` 方法设计成接收一个集合，所以这里把单个员工 `id` 包装成一个 `List` 传进去。

一句话理解：

> 修改员工时，主表直接 `update`，子表工作经历采用“先删旧数据，再插新数据”的处理方式。

### 5. 事务控制

修改员工功能同样需要事务，因为它至少包含三步数据库操作：

1. 更新 `emp`
2. 删除旧 `emp_expr`
3. 插入新 `emp_expr`

如果中间任何一步失败，都可能导致数据只更新一部分。

因此通常在 `update(Emp emp)` 方法上加：

```java
@Transactional(rollbackFor = Exception.class)
```

作用：

- 把“更新主表 + 删除旧经历 + 插入新经历”作为一个整体事务处理
- 如果出现异常，则整组操作一起回滚

一句话理解：

> 修改员工功能的事务边界包住的是整个 `update(Emp emp)` 业务方法，而不是某一条单独 SQL。

### 6. 主表更新 SQL

`empMapper.updateById(emp)` 对应的主表更新 SQL 通常写成：

```xml
<update id="updateById">
    UPDATE emp
    SET
        username = #{username},
        password = #{password},
        name = #{name},
        gender = #{gender},
        phone = #{phone},
        job = #{job},
        salary = #{salary},
        image = #{image},
        entry_date = #{entryDate},
        dept_id = #{deptId},
        update_time = #{updateTime}
    WHERE id = #{id}
</update>
```

说明：

1. `WHERE id = #{id}` 用于确定要修改哪一个员工
2. 主表更新使用 `UPDATE ... SET ... WHERE ...`，而不是重新插入
3. `update_time` 会随着每次修改一起更新

一句话理解：

> 修改员工主表时，通过 `update emp set ... where id = #{id}` 根据员工 id 更新基础信息，并同步更新 `update_time`。

### 7. 动态更新优化

前面的固定更新写法虽然能用，但存在两个明显问题：

1. 不够灵活
2. 扩展性较差

因为固定写法会把所有字段都写进：

```xml
SET ...
```

即使某个字段没有值，或者当前场景下并不需要更新，也会参与更新。

所以修改员工功能通常会继续优化成：**动态更新**。

#### 优化思路

使用 MyBatis 的：

- `<if>`
- `<set>`

来实现“有值的字段才更新”。

例如：

```xml
<update id="updateById">
    update emp
    <set>
        <if test="username != null and username != ''">username = #{username},</if>
        <if test="password != null and password != ''">password = #{password},</if>
        <if test="name != null and name != ''">name = #{name},</if>
        <if test="gender != null">gender = #{gender},</if>
        <if test="phone != null and phone != ''">phone = #{phone},</if>
        <if test="job != null">job = #{job},</if>
        <if test="salary != null">salary = #{salary},</if>
        <if test="image != null and image != ''">image = #{image},</if>
        <if test="entryDate != null">entry_date = #{entryDate},</if>
        <if test="deptId != null">dept_id = #{deptId},</if>
        <if test="updateTime != null">update_time = #{updateTime},</if>
    </set>
    where id = #{id}
</update>
```

说明：

- `<if>`：控制某个字段是否参与更新
- `<set>`：自动生成 `set` 关键字，并自动去掉最后多余的逗号

#### 和前面动态 SQL 的对应关系

- 条件查询：`<if> + <where>`
- 动态更新：`<if> + <set>`

一句话理解：

> 修改员工 SQL 优化成动态更新后，通常通过 `<if> + <set>` 实现“有值的字段才更新”，从而让更新语句更灵活。

## 十三、全局异常处理

### 1. 为什么需要全局异常处理器

在员工管理、文件上传、事务处理这些功能中，异常可能出现在：

- Controller
- Service
- Mapper

如果每个接口方法里都自己写 `try-catch`，代码会很乱，而且返回给前端的错误格式也不统一。

所以通常会增加一个：**全局异常处理器**，统一完成：

1. 捕获异常
2. 记录日志
3. 返回统一错误结果

一句话理解：

> 全局异常处理器的作用是：集中处理项目中的异常，统一日志和响应结果，避免在每个 Controller 方法里重复写 `try-catch`。

### 2. 基本写法

全局异常处理器常见写法如下：

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler
    public Result handleException(Exception e) {
        log.error("程序出错啦~", e);
        return Result.error("出错啦，请联系管理员~");
    }
}
```

这里最关键的两个注解是：

- `@RestControllerAdvice`：声明这是一个全局异常处理组件
- `@ExceptionHandler`：声明当前方法专门用于处理某种异常

说明：

1. 只要项目中抛出了没有被单独处理的异常，就会进入这里
2. 在这里统一打印日志，方便排查问题
3. 在这里统一返回 `Result.error(...)`，前端拿到的就是规范响应，而不是直接看到异常栈

一句话理解：

> 正常结果还是按原链路返回；一旦出现异常，就转到全局异常处理器统一处理。

### 3. 为什么还要单独处理 `DuplicateKeyException`

如果只写一个通用的：

```java
@ExceptionHandler
public Result handleException(Exception e)
```

虽然能兜底，但所有异常都会被统一返回成类似：

```text
出错啦，请联系管理员~
```

这样用户虽然知道失败了，但并不知道具体原因。

而员工管理里有一个很常见的异常场景：

> 新增或修改员工时，用户名等唯一字段重复，数据库抛出 `DuplicateKeyException`

对于这种异常，如果还是只返回“服务器异常”，就不够友好。

所以通常会再加一个更具体的异常处理方法，例如：

```java
@ExceptionHandler
public Result handleDuplicateKeyException(DuplicateKeyException e) {
    log.error("程序出错啦~", e);
    String message = e.getMessage();
    int i = message.indexOf("Duplicate entry");
    String errMsg = message.substring(i);
    String[] arr = errMsg.split(" ");
    return Result.error(arr[2] + " 已存在");
}
```

这段代码的思路是：

1. 先捕获数据库抛出的 `DuplicateKeyException`
2. 从异常信息里提取出重复值
3. 拼成更友好的提示，比如：

```text
zhangsan 已存在
```

也就是说：

> 对于用户能理解、也确实常见的异常，可以单独处理，返回更明确、更友好的提示。

### 4. 通用异常和特定异常的关系

这里其实是一种“分层处理”思路：

- **特定异常单独处理**：例如 `DuplicateKeyException`
- **其他异常统一兜底**：例如 `Exception`

这样做的好处是：

1. 重要且常见的异常可以给出更明确提示
2. 其余异常不用每种都手写，仍然有一个统一兜底

一句话理解：

> 全局异常处理中，能明确识别并友好提示的异常单独处理；其他异常再交给通用 `Exception` 处理器兜底。

### 5. 当前场景下的理解重点

在员工管理模块中，全局异常处理器的价值主要体现在：

1. 删除、修改、上传、事务等功能出现异常时，不用在每个接口里写重复的 `try-catch`
2. 对数据库唯一约束冲突这类异常，可以给前端返回更友好的提示
3. 整个项目的错误响应格式保持统一

最短记法：

```text
通用异常：统一兜底
重复键异常：单独处理，返回更友好的提示
```

## 十四、员工信息统计

### 1. 统计功能的核心目标

员工信息统计不再是查单个员工，而是：

> 按某个维度对员工数据进行分组统计，并把统计结果返回给前端做图表展示。

当前阶段先做两类统计：

1. 职位统计
2. 性别统计

其中前端图表使用的是 **ECharts**，所以后端返回的数据结构不能只考虑“查出来”，还要考虑：

> **是否方便 ECharts 直接消费。**

### 2. 为什么要适配 ECharts

如果只是普通统计 SQL，数据库可能返回的是类似：

```text
job   count
1     1
2     1
3     2
4     6
5     8
6     13
```

但 ECharts 更常见、也更顺手的数据形式通常是：

1. 一组横轴分类数据
2. 一组纵轴数值数据

比如职位统计图，前端最想拿到的其实是：

```json
{
  "jobList": ["教研主管","学工主管","其他","班主任","咨询师","讲师"],
  "dataList": [1,1,2,6,8,13]
}
```

也就是说：

- `jobList`：横轴分类列表
- `dataList`：对应的数量列表

一句话理解：

> 统计接口不是随便返回数据库原始结果，而是要按图表组件最容易使用的结构组织数据。

### 3. 职位统计的返回结构

在当前课程中，职位统计通常会定义一个专门的数据对象，例如：

```java
@Data
@NoArgsConstructor
@AllArgsConstructor
public class JobOption {
    private List jobList;   // 职位列表
    private List dataList;  // 人数列表
}
```

它的作用就是：

> 专门为前端 ECharts 的柱状图返回职位统计数据。

其中：

- `jobList`：存职位名称
- `dataList`：存每个职位对应的人数

### 4. 当前阶段要抓住的重点

员工信息统计这里最关键的不是“图怎么画”，而是：

1. 统计类接口通常是按维度分组查询
2. 返回结果要适配 ECharts 的使用方式
3. 所以常常会定义专门的 VO / Option 对象，而不是直接把数据库原始结果原样返回

最短记法：

```text
统计查询：按维度 group by
返回结构：按 ECharts 需要的格式封装
```

一句话总结：

> 员工信息统计的核心是：按职位或性别分组统计员工数量，并把结果封装成适合 ECharts 直接使用的数据结构返回给前端。

### 5. 职位统计中的 `CASE` 表达式

职位统计最基础的 SQL 虽然可以先写成：

```sql
select job, count(*)
from emp
group by job;
```

但这样查出来的往往只是职位编号，例如：

```text
1  1
2  1
3  2
4  6
5  8
6  13
```

对于前端 ECharts 来说，这样的结果不够直观，因为图表更适合直接显示职位名称。

所以通常会在 SQL 中使用 `CASE` 表达式，把职位编号直接转换成可读名称，例如：

```sql
select
    (case job
        when 1 then '教研主管'
        when 2 then '学工主管'
        when 3 then '其他'
        when 4 then '班主任'
        when 5 then '咨询师'
        when 6 then '讲师'
     end) as job,
    count(*) as count
from emp
group by job;
```

这样查出来的结果就更适合后面继续封装成：

```json
{
  "jobList": ["教研主管","学工主管","其他","班主任","咨询师","讲师"],
  "dataList": [1,1,2,6,8,13]
}
```

一句话理解：

> `CASE` 表达式的作用，是在统计 SQL 中把数据库里的编码值直接转换成前端更容易展示的可读文本。

### 6. 职位统计的三层职责

职位统计这一步，不是单纯查 SQL，而是要把数据库统计结果进一步整理成 ECharts 可以直接使用的结构。

#### Controller 层

Controller 负责：

1. 接收前端请求
2. 调用 Service 方法
3. 返回结果

也就是说，Controller 这里只负责把“我要看职位统计”的请求交给后端业务层处理，不负责自己做分组统计和图表数据组装。

#### Service 层

Service 是职位统计的核心。

它通常负责：

1. 调用 Mapper 查询职位统计原始数据
2. 解析查询结果
3. 封装成 ECharts 需要的数据对象

在当前课程中，这个封装对象通常就是：

```java
public class JobOption {
    private List jobList;   // 职位列表
    private List dataList;  // 人数列表
}
```

也就是说，Service 的关键工作不是“写 SQL”，而是：

> 把数据库查出来的 `pos + num` 结果，转换成 `jobList + dataList` 结构。

#### Mapper 层

Mapper 负责真正执行统计 SQL。

它的职责通常是：

1. 按 `job` 分组
2. 用 `case` 把职位编号转换成职位名称
3. 统计每种职位的人数
4. 返回原始统计结果

一句话理解：

> Mapper 负责把“职位 + 人数”查出来，Service 负责把它变成图表结构，Controller 负责接请求和回结果。

### 7. 当前阶段的完整链路

职位统计的完整处理流程可以压成：

```text
前端请求职位统计
-> Controller 接请求
-> Service 调用 Mapper 查询统计结果
-> Service 组装 JobOption(jobList + dataList)
-> 返回给前端 ECharts 展示
```

一句话总结：

> 职位统计中，Mapper 负责分组统计，Service 负责封装 `JobOption`，Controller 负责接请求并返回最终结果。

### 8. 职位统计的 Controller / Service / Mapper 实现

#### Controller

职位统计通常会单独放在 `ReportController` 中，例如：

```java
@RequestMapping("/report")
@RestController
public class ReportController {

    @Autowired
    private ReportService reportService;

    @GetMapping("/empJobData")
    public Result getEmpJobData() {
        log.info("统计员工职位人数");
        JobOption jobOption = reportService.getEmpJobData();
        return Result.success(jobOption);
    }
}
```

请求路径通常是：

```text
GET /report/empJobData
```

说明：

- `ReportController` 专门放报表统计类接口
- `getEmpJobData()` 只负责接请求、调 Service、回结果

#### Service

Service 层的核心工作是：

1. 调用 Mapper 获取原始统计结果
2. 把原始结果拆成 `jobList` 和 `dataList`
3. 封装成 `JobOption`

例如：

```java
@Override
public JobOption getEmpJobData() {

    // 1. 调用 mapper 接口，获取统计数据
    List<Map<String, Object>> list = empMapper.countEmpJobData();

    // 2. 组装结果，并返回
    List<Object> jobList = list.stream().map(dataMap -> dataMap.get("pos")).toList();
    List<Object> dataList = list.stream().map(dataMap -> dataMap.get("num")).toList();

    return new JobOption(jobList, dataList);
}
```

这里 `list` 中的每一行大概类似：

```text
{pos=教研主管, num=1}
```

所以 Service 实际上做的是“拆列”：

- 把 `pos` 这一列提取出来，形成 `jobList`
- 把 `num` 这一列提取出来，形成 `dataList`

一句话理解：

> Service 层负责把数据库原始统计结果转换成 ECharts 最容易直接使用的结构。

#### Mapper

Mapper 里真正执行统计 SQL，常见写法如下：

```xml
<select id="countEmpJobData" resultType="java.util.Map">
    select
        (case
            when job = 1 then '班主任'
            when job = 2 then '讲师'
            when job = 3 then '学工主管'
            when job = 4 then '教研主管'
            when job = 5 then '咨询师'
            else '其他'
         end) pos,
        count(*) num
    from emp
    group by job
    order by num
</select>
```

这里有两个关键点：

1. 使用 `case` 把职位编号转换成职位名称
2. 使用：

```xml
resultType="java.util.Map"
```

表示每一行查询结果先映射成一个 `Map`，例如：

```text
{pos=班主任, num=7}
```

这样 Service 层就可以通过：

```java
dataMap.get("pos")
dataMap.get("num")
```

把它们再拆成图表所需的两个列表。

### 9. 当前阶段的理解重点

职位统计这一段的重点不是“只会写分组 SQL”，而是：

1. SQL 先负责把“职位名称 + 人数”查出来
2. Mapper 把每一行先映射成 `Map`
3. Service 再把多行 `Map` 拆成 `jobList + dataList`
4. 最后封装成 `JobOption` 返回给前端图表

最短记法：

```text
Mapper：查 pos + num
Service：拆成 jobList + dataList
Controller：返回 JobOption
```

### 10. `CASE` 的两种常见写法小结

`CASE` 作为流程控制函数，常见有两种写法：

#### 语法一：搜索 `CASE`

```sql
case
    when 条件1 then 结果1
    when 条件2 then 结果2
    else 结果n
end
```

特点：

- 每个 `when` 后面直接写条件
- 适合区间判断、多条件判断、复杂分类

例如：

```sql
case
    when salary < 5000 then '低'
    when salary >= 5000 and salary < 10000 then '中'
    else '高'
end
```

#### 语法二：简单 `CASE`

```sql
case 表达式
    when 值1 then 结果1
    when 值2 then 结果2
    else 结果n
end
```

特点：

- 先写一个字段或表达式
- 后面的 `when` 主要做等值匹配
- 适合编号转名称、枚举值转文本

例如职位统计里这种：

```sql
case job
    when 1 then '班主任'
    when 2 then '讲师'
    when 3 then '学工主管'
    when 4 then '教研主管'
    when 5 then '咨询师'
    else '其他'
end
```

最短记法：

```text
复杂条件分类 -> 语法一
等值映射转换 -> 语法二
```

一句话理解：

> `CASE` 第一种写法适合条件判断，第二种写法适合字段值映射；员工职位统计这种“编号转名称”的场景，通常更适合第二种。

### 11. 性别统计的需求特点

职位统计做的是柱状图，所以后端返回的是：

- 一组分类列表 `jobList`
- 一组数值列表 `dataList`

而性别统计这里使用的是 **ECharts 环形图 / 饼图**，所以返回结构会不一样。

从当前页面原型和响应数据来看，前端更需要的格式通常是：

```json
[
  {"name": "男性员工", "value": 5},
  {"name": "女性员工", "value": 6}
]
```

也就是说，性别统计不是拆成两个并行列表，而是：

> 直接返回一个对象数组，每个对象同时带 `name` 和 `value`。

#### 为什么和职位统计不一样

因为图表类型不同：

- **柱状图** 更适合：
  - 横轴分类列表
  - 纵轴数值列表
- **饼图 / 环形图** 更适合：
  - `[{name: ..., value: ...}, ...]`

所以这里再次说明一个很重要的思路：

> 统计接口返回什么结构，不只是看 SQL 查出了什么，更要看前端图表组件最方便消费什么。

#### 当前阶段要抓住的重点

性别统计的核心不是新学一套完全不同的统计，而是：

1. 依然要按维度分组统计人数
2. 只是因为图表形式不同，返回结果结构也跟着改变

最短记法：

```text
职位统计 -> jobList + dataList
性别统计 -> [{name, value}, {name, value}]
```

一句话理解：

> 性别统计和职位统计的统计思路类似，但由于前端使用的是饼图/环形图，所以后端更适合直接返回 `name + value` 形式的对象数组。

### 12. 性别统计的 Controller / Service / Mapper 实现

#### Controller

性别统计通常也放在 `ReportController` 中，例如：

```java
@GetMapping("/empGenderData")
public Result getEmpGenderData() {
    log.info("统计员工性别人数");
    List<Map<String, Object>> genderList = reportService.getEmpGenderData();
    return Result.success(genderList);
}
```

请求路径通常是：

```text
GET /report/empGenderData
```

说明：

- Controller 负责接请求
- 调用 `reportService.getEmpGenderData()`
- 直接返回适配饼图/环形图的数据列表

#### Service

Service 层这里相对职位统计更简单，因为前端需要的本来就是：

```json
[
  {"name": "男性员工", "value": 5},
  {"name": "女性员工", "value": 6}
]
```

而 Mapper 查询出来的结构已经和这个格式比较接近，所以 Service 通常只需要直接转发：

```java
@Override
public List<Map<String, Object>> getEmpGenderData() {
    return empMapper.countEmpGenderData();
}
```

一句话理解：

> 性别统计因为查询结果天然接近前端饼图需要的数据结构，所以 Service 层不需要像职位统计那样再拆成两个列表。

#### Mapper

Mapper 里真正执行统计 SQL，常见写法如下：

```xml
<select id="countEmpGenderData" resultType="java.util.Map">
    select
        if(gender = 1, '男性员工', '女性员工') name,
        count(*) value
    from emp
    group by gender
</select>
```

这条 SQL 完成了三件事：

1. 按 `gender` 分组
2. 用 `if(...)` 把性别编号转换成可读文本
3. 统计每组人数，并直接映射为：
   - `name`
   - `value`

最终每一行大概类似：

```text
{name=男性员工, value=5}
```

所以整个查询结果天然就是前端图表非常容易消费的结构。

### 13. 关于 `@MapKey` 的一个小提醒

截图里 Mapper 接口上可能会看到类似：

```java
@MapKey("name")
List<Map<String, Object>> countEmpGenderData();
```

这里要注意一个理解点：

> `@MapKey` 更常见的用途，是配合返回值为 `Map<K, V>` 时，指定哪一列作为这个 `Map` 的 key。

而当前性别统计这里，返回的是：

```java
List<Map<String, Object>>
```

也就是说，我们本来就是想拿到“多行结果组成的列表”，每一行再是一个 `Map`。

因此从常规理解上说：

- 当前场景的核心仍然是：
  ```xml
  resultType="java.util.Map"
  ```
- `@MapKey` 不是这一节真正要抓的重点

复习时更建议先记住这条主线：

```text
Mapper 返回 List<Map<String,Object>>
每一行就是一个 {name, value}
Controller 直接返回给前端图表
```

一句话总结：

> 性别统计中，Mapper 查询结果本身就已经接近 ECharts 饼图所需的数据结构，所以 Service 可以直接返回 `List<Map<String,Object>>`，整体链路比职位统计更简单。

### 14. `if` 流程控制函数小结

在性别统计里，我们用到了：

```sql
if(gender = 1, '男性员工', '女性员工')
```

这里的 `if` 属于 MySQL 常见的流程控制函数。

#### `if(expr, val1, val2)`

含义：

> 如果表达式 `expr` 成立，返回 `val1`；否则返回 `val2`。

例如：

```sql
if(gender = 1, '男性员工', '女性员工')
```

表示：

- 如果 `gender = 1`，返回“男性员工”
- 否则返回“女性员工”

这很适合当前这种：

> 只有两种分支结果的简单分类场景

#### `ifnull(expr, val1)`

含义：

> 如果 `expr` 不为 `null`，取 `expr` 本身；否则取 `val1`。

例如：

```sql
ifnull(phone, '未填写')
```

表示：

- 如果 `phone` 有值，就返回 `phone`
- 如果 `phone` 是 `null`，就返回“未填写”

#### 和前面 `case` 的关系

- `case`：更适合多分支分类
- `if`：更适合二选一判断
- `ifnull`：更适合空值兜底

最短记法：

```text
if：二选一
ifnull：空值兜底
case：多分支分类
```

一句话理解：

> 性别统计里使用 `if`，是因为这里只有“男性员工 / 女性员工”两种分支结果，用 `if` 比 `case` 更简洁。
