# 登录认证学习笔记

## 一、当前学习阶段

当前主线仍然属于 `9. Web项目`。

员工管理模块已经基本闭环，接下来进入一个很关键的主题：

> 用户登录成功后，系统如何识别“你是谁”，以及后续接口为什么不能让任何人随便访问。

登录认证这一段，通常会连着学这些内容：

- 登录功能
- 登录校验
- 会话技术
- `Session`
- `Token`
- `JWT`
- `Filter`
- `Interceptor`

---

## 二、先区分两个概念

### 1. 登录

登录强调的是：

> 用户把账号和密码提交给服务端，服务端校验是否正确。

也就是说，登录关注的是“第一次身份确认”。

典型流程：

1. 用户输入用户名和密码
2. 前端把账号密码提交给后端
3. 后端查询数据库或其他用户信息源
4. 校验成功则返回成功结果
5. 校验失败则返回失败结果

### 2. 认证

认证强调的是：

> 用户登录成功之后，后续每次请求如何证明自己仍然是合法用户。

因为用户不可能每访问一个接口都重新输入一次密码，所以系统需要一种机制保存登录状态。

---

## 三、为什么必须做登录认证

如果系统没有登录认证，会出现这些问题：

- 任何人都能直接访问员工列表
- 任何人都能新增、修改、删除员工
- 后端无法区分“已登录用户”和“未登录用户”
- 用户关闭页面后，系统也不知道是否还应该允许访问

所以登录认证的核心目标可以压成一句话：

> 登录负责确认身份，认证负责维持身份。

---

## 四、登录功能的基本链路

在三层架构中，登录通常还是按熟悉的链路走：

```text
前端提交用户名密码
-> Controller 接收参数
-> Service 处理登录逻辑
-> Mapper 查询用户
-> 数据库返回结果
-> Service 判断是否登录成功
-> 返回登录结果
```

### 1. Controller 层职责

Controller 负责：

- 接收前端传来的登录参数
- 调用 Service
- 返回统一响应结果

它不应该自己写 SQL，也不应该自己做复杂业务判断。

### 2. Service 层职责

Service 是登录逻辑的核心。

常见职责：

1. 调用 Mapper 查询用户信息
2. 判断用户名和密码是否匹配
3. 决定是否生成登录标识
4. 把登录结果返回给 Controller

### 3. Mapper 层职责

Mapper 负责真正查询数据。

例如：

- 根据用户名查询用户
- 根据用户名和密码联合查询用户

如果课程阶段偏基础，很多时候会直接写成“用户名 + 密码一起查”。

如果想更规范一些，也可以先查用户，再单独比对密码。

---

## 五、登录成功之后，系统要保存什么

登录成功之后，系统至少要保存一类信息：

> 当前这个请求对应的是哪个已登录用户。

常见保存内容包括：

- 用户 id
- 用户名
- 用户角色
- 登录时间
- 令牌字符串

这里最关键的不是“保存得多不多”，而是：

> 后续请求来到后端时，系统要能重新识别出这个用户。

---

## 六、会话技术的核心理解

会话可以简单理解为：

> 用户从开始访问系统，到离开系统这一段连续交互过程。

在一次会话中，后端通常要记住这个用户的身份状态。

也就是说，登录认证不是只处理一次请求，而是要处理“一串连续请求”。

---

## 七、`Session`、`Token`、`JWT` 的关系

### 1. `Session`

`Session` 是服务端会话技术。

基本思路：

1. 用户登录成功
2. 服务端创建一个 `Session`
3. 把用户信息保存到 `Session` 中
4. 把 `SessionId` 返回给客户端
5. 客户端后续请求带着 `SessionId`
6. 服务端根据 `SessionId` 找到对应会话

特点：

- 用户状态主要保存在服务端
- 实现直观
- 传统项目里很常见

### 2. `Token`

`Token` 可以理解成：

> 登录成功后，由服务端签发给客户端的一段身份凭证。

后续请求时，客户端把这个令牌带回来，服务端据此判断当前用户是否已登录。

特点：

- 更适合前后端分离项目
- 通常放在请求头中
- 服务端不一定需要像 `Session` 那样保存大量会话状态

### 3. `JWT`

`JWT` 是一种常见的 `Token` 格式。

全称：

```text
JSON Web Token
```

它本质上仍然是令牌，只是这个令牌遵循了一种固定格式。

常见特点：

- 可以在令牌中携带用户信息
- 可以设置过期时间
- 可以通过签名防止内容被随意篡改

所以三者关系可以简单记成：

```text
Session：服务端保存状态
Token：客户端带令牌
JWT：一种常见的 Token 格式
```

---

## 八、为什么前后端分离里更常见 `Token / JWT`

前后端分离项目里，前端和后端通常是分开的。

这种场景下，使用 `Token / JWT` 往往更自然，因为：

- 前端只需要保存令牌
- 后续请求统一把令牌放到请求头
- 后端接口更容易统一校验
- 更适合移动端、小程序、浏览器前后端分离等场景

一句话：

> `Session` 更像“服务端记住你”，`Token / JWT` 更像“客户端自己带着身份证明来”。

---

## 九、登录校验到底校验什么

登录校验不是再校验一次账号密码，而是校验：

- 当前请求有没有带登录标识
- 登录标识是否合法
- 登录标识有没有过期
- 这个请求是否属于需要登录后才能访问的资源

所以登录校验的重点是：

> 拦住未登录请求，放行已登录请求。

---

## 十、登录校验常见落点

登录校验一般不会写在每一个 Controller 方法里重复判断。

更常见的做法是统一拦截请求。

常见落点有两个：

- `Filter`
- `Interceptor`

### 1. `Filter`

`Filter` 是 Servlet 规范中的过滤器。

它的特点是：

- 作用在请求进入 Spring MVC 之前
- 能对请求和响应做统一处理
- 适合做通用型过滤逻辑

例如：

- 字符编码处理
- 敏感词过滤
- 登录校验

### 2. `Interceptor`

`Interceptor` 是 Spring MVC 提供的拦截器。

它的特点是：

- 更贴近 Controller
- 更方便针对接口做拦截和放行配置
- 在 SpringBoot 项目里做登录校验非常常见

例如：

- 登录检查
- 权限判断
- 请求日志记录

### 3. 二者怎么理解

简单理解：

> `Filter` 更靠前、更底层；`Interceptor` 更靠近业务接口。

如果当前课程是 SpringBoot Web 项目，登录校验很多时候会更偏向讲 `Interceptor`。

---

## 十一、登录认证这一段的典型流程

把整段主线压缩一下，通常会变成：

```text
1. 用户输入用户名密码
2. 后端校验成功
3. 后端生成 Session / Token / JWT
4. 前端保存登录标识
5. 后续请求带着登录标识访问接口
6. Filter 或 Interceptor 统一校验
7. 合法则放行，不合法则拦截
```

这就是登录认证的完整闭环。

---

## 十二、当前阶段最值得先记住的点

1. 登录和认证不是一回事
2. 登录是第一次校验身份
3. 认证是后续每次请求持续证明身份
4. `Session` 偏服务端存状态
5. `Token / JWT` 偏客户端携带凭证
6. 登录校验通常不写在每个接口里，而是统一交给 `Filter` 或 `Interceptor`

---

## 十三、今天继续学时可以重点追这 4 个问题

1. 登录接口具体接收哪些参数，返回什么结果
2. 课程当前用的是 `Session`、普通 `Token`，还是 `JWT`
3. 登录标识最终放在请求头、Cookie，还是其他位置
4. 登录校验最终是落在 `Filter` 还是 `Interceptor`
